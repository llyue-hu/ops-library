# 07 · 安全抓取与批量入库

**适用**：从若干公开来源批量拉一批文件（PDF、md、JSON），再解析成结构化成品的流程。特点是：**一次抓完，反复解析**。

**不适用**：需要模拟点击、登录、绕验证码的站；这类别做。

---

## 1. 目录布局（照抄即可）

```
_work/
  <task>/
    raw/            # 原样落地，不解析、不改名逻辑以外的任何东西
    parsed/         # 解析产物（JSON/文本），按来源或年份命名
    out/            # 最终交付
    manifest.json   # 每个 raw 文件的 url / 大小 / sha256 / 抓取时间
    _scratch/       # 临时草稿，可随时删
```

`raw` 与 `parsed` 分开的意义：解析规则写错时，不用重新联网；换执行者/换 agent 时，接手的成本只有 `parsed`。

## 2. 流程

```
清单 → 抓取（04 的 fetch_cache.py）→ 校验 → 落地 raw → 解析 → 校验 → 写 manifest
```

每一步都可重跑，重跑时命中缓存直接跳过。

## 3. 五个硬规则

**a) 先落地，再解析。** 不要边下边 parse 流式内容。半截文件会让解析器报出莫名其妙的结构错误，排查成本极高。

**b) 原子落盘。** 写 `<name>.part`，校验通过再 `os.replace`。看到 `.part` 就说明没完成。

**c) 幂等：以产物存在为完成标志。** 重跑先检查 `dest` 是否已完整；只有 `--force` 才覆盖。这样中断后重跑不会重复下载。

**d) 串行 + 间隔。** 批量抓取默认串行，每次间隔 0.5–1 秒。并发是 403/429 的主要来源。遇到 403/429/验证码**立即停**，不要换 IP 重试。

**e) 记录来源。** 每个产物要能回答：这份内容从哪来、什么时候抓的、是不是被改动过。写进 `manifest.json`，也写进成品文件的页眉（本项目的【来源】字段就是这么来的）。

## 4. manifest 最小字段

```json
{
  "raw/2010.pdf": {
    "url": "https://...",
    "mirror_used": "https://cdn.jsdelivr.net/...",
    "bytes": 1243228,
    "sha256": "...",
    "fetched_at": "2026-10-26T02:57:12+08:00"
  }
}
```

`mirror_used` 很有用：同一个文件从不同镜像拿到的字节可能不同（缓存滞后），出问题先看这里。

## 5. 去重

- 同名不同源：先比 `sha256`，相同就只留一份。
- 同源不同名（`xxx (1).pdf`）：按 sha256 合并。
- 内容级去重之后再做业务去重（同一年份两份答案），后者要人工判断。

## 6. 抓取源优先级

1. 官方/原始发布方（最可信，但可能慢）。
2. 可信镜像（04 里的 jsDelivr / ghfast）。
3. 第三方转载（只在前两者都拿不到时用，且必须在成品里注明）。

同一份数据**至少两个来源交叉核对**再入库，尤其是“答案”“数值”这类会被反复引用的字段。多源不一致时按**内容**对齐，不按位置/编号对齐——不同转载会把选项顺序重排，按字母比一定错。

## 7. 坑

- **半截文件**：只看“文件存在”不够，必须校验体积/hash，PDF 还要能抽出文本。
- **编码**：HTML/md 可能是 GBK；先探测再解码，不要默认 UTF-8。
- **站点改版**：解析器要按“结构特征”定位（标题层级、固定前缀），不要依赖绝对行号。
- **重复入库**：解析产物命名带年份/版本，别用 `output.json` 这种会被覆盖的名字。
- **清理**：`_scratch/` 可以删，`raw/` 在成品验收通过前不要删。

## 8. 交接检查单

换人/换 agent 接手时，对方只需要三样东西：

1. `raw/` 是否齐全（对比 manifest 的条数）；
2. `parsed/` 是否覆盖全部输入（缺哪年一目了然）；
3. 成品验收脚本与 spec（见 09）。

满足这三条，接手者不用重新联网也能把活干完。
